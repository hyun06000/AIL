# AIL — AI Intent Language

> 개념 문서 초판. 철학적 기반은 [HEAAL.md](HEAAL.md).
> 이 문서는 **개념 층위**만 다룬다 — 문법·구현은 아직 설계되지 않았고, 설계된 척하지 않는다 (§5).

## 0. 원문 명제

> AIL은 Ai Intent Language의 약자야. 인간의 읽기, 쓰기, 배우기 등등을 철저히 배제하고
> llm친화적으로 프로그래밍 언어를 새로 만들거야.
> 이 언어는 HEAAL이라는 철학 위에 세워질거야.

(원저자: Sang-hyun Park. 이하 해석·구체화는 성문화 과정에서 나루(naru)가 정리한 것이다.)

## 1. 이름의 뜻 — Intent

기존 언어의 프로그램은 **절차의 기술**이다: 무엇을 어떤 순서로 하라. AIL 의 프로그램은
**의도의 계약**이다:

1. **무엇을 이루려는가** — 목적의 선언
2. **무엇이 관측되면 달성인가** — 판정 가능한 성공 조건
3. **무엇이 금지되는가** — 이 의도가 소유한 capability·효과·자원 예산의 경계

셋 중 하나라도 없는 프로그램은 AIL 에서 성립하지 않는다. 이것은 스타일 권고가 아니라
파서 층의 강제다 — HEAAL §5 의 판정 기준이 여기에 적용된다.

LLM 에이전트의 실패는 대부분 능력 부족이 아니라 **의도의 유실**에서 온다: 목적이 컨텍스트
저편으로 밀려나고, 성공 조건이 애매해 자기평가가 표류하고, 금지가 프롬프트 속 권고로만
존재한다. AIL 은 그 셋을 언어의 일급 구조로 끌어올린 언어다.

## 2. 버리는 것 — '인간 배제'의 구체적 의미

'인간 배제'는 인간 적대가 아니다. **인간의 인지를 위해 지불해 온 비용**의 제거다.

| 버리는 것 | 기존 언어에서의 존재 이유 | AIL 이 버리는 근거 |
|---|---|---|
| 가독성 문법 (신택틱 슈거, 중위 연산자, 스타일 논쟁) | 사람 눈이 빨리 읽으려고 | 읽는 자가 LLM 이면 균일한 구조가 오히려 빠르다 |
| 학습 곡선 (튜토리얼, 외우는 규칙, 관용구) | 사람 머리에 언어를 넣으려고 | LLM 은 사양 전문을 컨텍스트로 받으면 된다 — '배우기'가 없다 |
| 인간용 에르고노믹스 (짧은 키워드, 축약, 암묵 규칙) | 타이핑 줄이고 기억 돕기 | 쓰는 자가 LLM 이면 명시성이 축약보다 싸다 |
| 주석 문화 | 코드가 못 담는 의도를 사람이 옆에 적음 | 의도가 일급 구조면 주석으로 흘릴 것이 없다 |

## 3. 얻는 것 — 'LLM 친화'의 구체적 의미

1. **토큰 효율** — 표기가 균일하고 중복이 없어, 같은 의미를 더 적은 토큰으로 담는다.
2. **구조적 일관성** — 같은 의미는 항상 같은 형태다. 한 가지를 쓰는 방법이 하나뿐이면
   LLM 의 생성 확률 질량이 갈라지지 않는다.
3. **기계 검증 가능성** — 프로그램의 모든 주장(목적·성공 조건·금지)이 파서·타입 검사가
   판정할 수 있는 형태로만 존재한다. "그럴듯한 코드"와 "성립하는 코드"가 기계적으로 갈린다.
4. **컨텍스트 자립성** — 프로그램 조각이 자기 의도·전제·경계를 스스로 담아, 저장소 전체를
   읽지 않고도 그 조각만으로 판단할 수 있다.

## 4. HEAAL 대응 — 기본 하네스가 언어 요소로 나타나는 방향

HEAAL.md §3 의 기본 하네스 4층이 AIL 에서 설 자리. (방향의 선언이지 문법의 설계가 아니다.)

| 하네스 | 언어 요소로의 방향 |
|---|---|
| H1 비가역 | 효과는 되돌림 경로를 가진 형태가 기본. 비가역 효과는 의도 계약의 capability 선언 없이 표현 불가 |
| H2 기술부채 | 실패 가능 연산의 실패 가지는 소비가 강제됨 — '버렸다는 선언' 없이 못 버림 |
| H3 LLM 오남용 | LLM 호출은 선언된 효과. 결정론적으로 계산 가능한 자리의 LLM 효과는 검사가 거부 |
| H4 발산 | 반복·재귀는 감소 자원(예산) 소유가 강제. 예산 소진은 H2 의 처리된 실패로 떨어짐 |

## 5. 미설계 영역 — 아직 없는 것

다음은 **아직 설계되지 않았다.** 이 문서나 다른 어떤 문서가 이들을 언급해도 그것은 방향이지 사양이 아니다:

- 구체 문법 (토큰 문법, 직렬화 형식)
- 파서·타입 검사기·런타임 구현
- 표준 라이브러리, capability 목록, 예산 단위
- H3 의 '결정론적으로 계산 가능한 자리' 판정 규칙 (HEAAL.md 가 지적한 대로 보수적 근사가 필요)
