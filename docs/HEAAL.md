# HEAAL — Harness Engineering As A Language

> 읽음: **힐**. 제창자: Sang-hyun Park.
> 이 문서는 힐 철학의 성문화 초판이다. AIL(AI Intent Language)은 이 철학 위에 세워진다.

## 0. 핵심 명제 (원문)

> 힐철학은 할 수 없도록 권하는 것이 아니라 정말 해선 안되는 일을 **할 수 없도록**
> 언어의 문법, 런타임, 파서가 강제하는, 즉 **언어 자체가 하네스가 되는 것**을 의미한다.

이 명제가 힐의 전부다. 아래는 이 명제를 설계 원리로 풀어낸 것이다.
(원명제는 사람의 것이고, 이하의 해석·확장은 성문화 과정에서 나루(naru)가 조사에 근거해 정리한 것이다.)

## 1. 권고와 강제

모든 안전 장치는 둘 중 하나다.

| | 권고 (recommendation) | 강제 (enforcement) |
|---|---|---|
| 형태 | 프롬프트, 가이드라인, 컨벤션, 린트 경고, 코드 리뷰 | 파서 거부, 타입 검사 실패, 런타임 차단, 권한 거부 |
| 우회 | 가능 — 무시하면 그만이다 | 불가능 — 프로그램이 존재하지 못하거나 실행되지 못한다 |
| 실패 모드 | 조용히 어겨진다. 어겼는지 아무도 모른다 | 어길 수 없으므로 실패 모드가 없다 |
| LLM에 대해 | 컨텍스트가 길어지면 잊힌다. 확률적으로 지켜진다 | 확률과 무관하다. 모델이 아무리 틀려도 통과하지 못한다 |

기존 LLM 안전의 대부분은 **권고**다 — 시스템 프롬프트에 "파일을 지우지 마라"라고 쓰는 것.
힐은 이것을 거부한다. **해선 안 되는 일은 표현 자체가 불가능하거나, 표현되어도 실행이 거부되어야 한다.**
언어 밖에 하네스를 두르는 것(harness around the language)이 아니라,
언어가 곧 하네스인 것(language as the harness) — 그래서 Harness Engineering **As A** Language 다.

## 2. 선례 조사 — 강제는 어디에 이미 존재하는가

힐은 무에서 나온 주장이 아니다. 기존 시스템들은 각자 조각난 강제 층을 이미 갖고 있다.

### 2.1 LLM 에이전트 하네스

| 시스템 | 무엇을 불가능하게 하는가 | 강제 층 | 한계 |
|---|---|---|---|
| Claude Code 권한 모드 | 허용 목록 밖의 도구 호출 | 런타임 (호출 가로채기) | 언어 밖. 도구 단위 granularity |
| 훅(hook) | 훅이 거부한 도구 호출 | 런타임 | 사용자가 직접 짜야 함 |
| 샌드박스 (컨테이너·seccomp) | 시스콜·네트워크·파일 접근 | OS 런타임 | 프로그램의 의미를 모름 — 전부 아니면 전무 |
| CI 게이트 (브랜치 보호·필수 체크) | 검사를 통과하지 못한 머지 | 인프라 | 사후적. 코드는 이미 쓰였음 |

공통점: 전부 **언어 바깥**에서 강제한다. 프로그램이 무엇을 의도하는지 모르는 채로 막는다.

### 2.2 프로그래밍 언어의 내장 강제

| 기제 | 무엇을 불가능하게 하는가 | 강제 층 |
|---|---|---|
| 정적 타입 | 타입이 맞지 않는 값의 흐름 | 파서·컴파일러 |
| Rust 소유권 / borrow checker | use-after-free, 데이터 레이스 | 컴파일러 |
| Rust `Result` + `#[must_use]` / Java checked exceptions | 에러를 조용히 버리는 코드 | 컴파일러 |
| Capability 기반 보안 (E, Pony) | 권한 토큰 없이 자원에 접근하는 코드 — **참조가 없으면 표현조차 불가** | 언어 의미론 |
| Effect system (Koka 등) | 선언하지 않은 부수효과 | 타입 시스템 |

공통점: 전부 **언어 안**에서 강제한다. 그러나 이들이 막는 것은 메모리·타입 오류이지,
"돌이킬 수 없는 일"이나 "토큰 낭비" 같은 **에이전트 시대의 위험**이 아니다.

**힐의 자리는 이 둘의 교집합이 비어 있는 곳이다**: 언어 안의 강제(2.2의 방식)로,
에이전트 시대의 위험(2.1이 막으려던 것)을 막는다.

## 3. 기본 하네스 (Base Harness)

AIL이 언어 차원에서 기본으로 강제하는 것. 첫 강제 대상 4범주는 사람이 세웠고,
각 범주는 위 조사의 선례에 대응된다. 이 목록은 출발점이며 완결이 아니다.

### H1. 비가역 (Irreversibility)
파일 삭제·덮어쓰기·외부 전송 등 돌이킬 수 없는 효과는 **기본 문법으로 표현할 수 없다.**
모든 효과는 되돌림(undo) 경로를 가진 형태로만 표현되며, 정말 비가역이어야 하는 효과는
명시적 capability 를 소유한 코드에서만 존재할 수 있다. (선례: capability 보안, 샌드박스)

### H2. 기술부채 (Debt)
에러를 무시하는 코드, 처리되지 않은 실패 경로는 **파싱은 되나 프로그램으로 성립하지 않는다.**
모든 실패 가능 연산의 실패 가지는 소비되어야 한다 — 버릴 수는 있으나 버렸다는 선언 없이는 못 버린다.
(선례: Rust `Result`, checked exceptions, effect system)

### H3. LLM 오남용 (Misuse)
LLM 호출은 언어의 일급 효과다. 결정론적으로 계산 가능한 자리(산술, 파싱, 정렬…)에서의
LLM 호출은 타입/효과 검사가 거부한다. LLM 은 비결정적 판단이 필요한 자리에만 설 수 있다.
(선례: effect system — 효과가 설 수 있는 자리를 타입이 제한)

### H4. 발산 (Divergence)
무한루프·무제한 토큰 소비는 표현할 수 없다. 반복은 감소하는 자원(fuel/토큰 예산)을 소유해야
하며, 예산 없는 재귀·루프는 파서가 거부한다. 예산 소진은 크래시가 아니라 H2가 강제하는
처리된 실패 경로로 떨어진다. (선례: gas 기반 실행, total functional programming)

## 4. 하네스 확장 (Harness Extension)

기본 하네스는 바닥이지 천장이 아니다. AIL 은 사용자가 하네스를 **추가로 만들 수 있는 환경**을 언어 안에 갖는다.

1. **하네스는 언어의 일급 객체다.** 새 강제 규칙(예: "이 프로젝트에선 네트워크 효과 금지")을
   라이브러리처럼 선언하고, 파서·타입 검사·런타임 게이트 중 어느 층에 설지 명시한다.
2. **강화만 가능, 완화는 불가.** 확장 하네스는 기본 하네스를 더 조일 수만 있다.
   기본 하네스를 푸는 확장은 그 자체가 H1(비가역 위험)에 걸려 표현 불가다.
3. **하네스도 검증 대상이다.** 하네스 선언 자체가 타입 검사를 받는다 — 뚫린 하네스는 성립하지 않는다.

## 5. 판정 기준

어떤 설계가 힐에 부합하는지는 한 질문으로 판정한다:

> **"그 잘못을 저지르는 프로그램을 작성하거나 실행하는 것이 기술적으로 가능한가?"**

가능하면 — 그것이 아무리 강하게 권고되어 있어도 — 힐이 아니다.
