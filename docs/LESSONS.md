# LESSONS — 전신 AIL-old에서 배운 것

> 같은 저자의 선행 시도 [hyun06000/AIL-old](https://github.com/hyun06000/AIL-old)
> (2026-04-16 ~ 05-26, v1.83)에 대한 분석. 참고 범위는 저자의 지시대로 둘로 한정한다:
> **왜 실패했는가**, 그리고 **그때 HEAAL은 무엇이었는가.**
> 이 문서의 관찰은 공개 저장소의 README·ROADMAP·CHANGELOG·docs/heaal.md·커밋 로그에 근거하며, 추측은 추측으로 표기한다.

## 1. 전신 개요 (사실만)

- 기간 약 6주, 버전 v1.83까지. 실제로 **동작하는 것들을 만들었다**: 파서가 있는 L1 언어
  (`pure fn`/`intent` 분리, `while` 금지, `Result` 강제, `evolve rollback_on`),
  Python 레퍼런스 + Go 인터프리터, 벤치마크 방법론(HEAAL Score), 파인튜닝 7B 모델,
  에이전트 런타임(L2)과 그 위의 서비스(Stoa·Mneme), L3(OS) 설계 문서.
- 즉 전신은 "아무것도 못 만든 실패"가 아니라 **만들면서 길을 잃은 실패**다.

## 2. 왜 실패했는가

### 원인 1 — 범위 발산: 저장소가 언어이기를 멈췄다 (관찰)

ROADMAP은 L1(언어)→L2(런타임)→L3(OS)의 3층 비전에 서비스·모델·벤치마크·커뮤니티 도구까지
품었고, 마지막 국면(v1.8x)의 커밋들은 언어가 아니라 CLI 서브커맨드·우선순위 큐·actuator다.
6주에 이 전부를 벌였다. 한 저장소가 언어이자 런타임이자 서비스이자 연구 프로젝트일 때,
"무엇이 관측되면 이 프로젝트가 성공인가"에 답할 수 없게 된다.

### 원인 2 — 하네스의 침식: 강제가 기능에 밀렸다 (관찰 + 해석)

핵심 주장은 "위험한 것은 문법적으로 불가능"이었으나, effect 목록이 자라며
(`http.*`, `state.*`, `schedule.every`, `env.read`, … 그리고 v1.83의 **`shell.run`**)
주장이 스스로 좁아졌다. 임의 셸 실행이 언어 안에 들어온 시점에, "불가능"은 "허용
목록이 크다"로 바뀐다. *(해석: 이것은 HEAAL §4의 '강화만 가능' 원칙이 없을 때 생기는
일이다 — 기능 압력은 언제나 완화 방향으로 분다.)*

### 원인 3 — 판정 기준의 이동: 철학이 벤치마크 점수가 됐다 (관찰 + 해석)

HEAAL은 "AIL vs Python 점수"(HEAAL Score, 모델별 claim boundary)로 측정되기 시작했고,
로드맵의 다음 일은 벤더 커버리지 확장이었다. *(해석: 측정 자체는 옳다. 문제는 측정이
북극성이 된 것 — "무엇을 불가능하게 만들 것인가"가 아니라 "점수를 어떻게 올릴 것인가"가
다음 사이클을 정하게 된다.)*

### 원인 4 — 결정의 기준이 사람 밖으로 나갔다 (관찰 + 해석)

말기의 에이전트 페르소나 조직(Telos·Tekton·Arche)과 "목표가 대화에서 창발하는 에이전트"
방향은, 우선순위 결정을 에이전트 사이클 안으로 옮겼다. *(해석: 현 저장소의 gil 규칙
"사람의 답이 기준이다"는 정확히 이 실패의 반대명제다.)*

## 3. 그때 HEAAL은 무엇이었나

전신의 [docs/heaal.md](https://github.com/hyun06000/AIL-old/blob/main/docs/heaal.md)는
이미 완성도 높은 정식화였고, 현 [HEAAL.md](HEAAL.md)와 같은 계보다:

- **같은 핵심 명제**: 하네스를 언어 밖에 두르지 말고 언어가 하네스가 되게 하라.
  "vibe coding → harness engineering → HEAAL"의 3층 진화 서사.
- **현 문서에 없는 기여 1 — guides/sensors 이중 구조**: 하네스를 사전 강제(guides:
  문법 제약)와 사후 관측(sensors: confidence·provenance·감사 추적)으로 나눴다.
  현 HEAAL.md는 강제(guides) 축만 성문화했다 — sensors 축은 미래 설계에서 다시 다룰 가치가 있다.
- **현 문서에 없는 기여 2 — 실증**: 문법 바닥(grammar floor)이 모델 등급 전반에서
  Python 대비 결과를 끌어올린다는 벤치마크 데이터가 실제로 존재한다
  (파서 통과율이 0인 모델에서는 바닥이 들어올릴 것이 없다는 경계 조건까지).
  철학이 측정 가능하다는 증거로서 계승한다 — 단, 원인 3의 교훈대로 측정은 도구이지 북극성이 아니다.

## 4. 계승과 폐기

| | 무엇 | 근거 |
|---|---|---|
| 계승 | HEAAL 핵심 명제와 3층 서사, guides/sensors 구분 | §3 — 같은 철학의 초판 |
| 계승 | "철학은 측정 가능하다"는 태도 (벤치마크의 존재) | §3 기여 2 |
| 계승 | 언어 수준 강제의 실물 선례 (`pure fn` 분리, `while` 금지, `Result` 강제, 되돌림 조건 필수) — **선례로만**, 사양으로 들여오지 않는다 | 현 AIL.md §5 미설계 원칙 |
| 폐기 | 언어·런타임·OS·서비스·모델·벤치마크를 한 저장소에서 동시 추진 | 원인 1 |
| 폐기 | 기능 압력에 의한 하네스 완화 (`shell.run` 류) | 원인 2 — HEAAL §4 '강화만 가능'이 이를 문법으로 막는다 |
| 폐기 | 점수를 북극성으로 삼는 로드맵 | 원인 3 |
| 폐기 | 우선순위 결정의 에이전트 위임 | 원인 4 — 사람의 답이 기준이다 (gil) |

## 5. 현 저장소에 거는 구속

1. **한 체인은 한 국면이다.** 문법 설계 체인이 열리면 그 체인은 문법만 한다. 런타임·서비스·벤치마크는 각자의 체인과 기준을 갖는다.
2. **effect 추가는 하네스 심사를 받는다.** 새 효과가 H1~H4 중 무엇을 약화시키는지 명시하지 못하면 들어오지 못한다.
3. **측정은 verify 스텝의 도구다.** 로드맵은 사람의 인테이크 답에서 나온다.
