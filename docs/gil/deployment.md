# 배포와 체인 전환

체인이 배포 순환의 한 국면을 이루는 방식과, 한 국면이 끝나면 사이클을 늘리지 않고 체인을 전환하는 규칙을 다룬다.

## 체인 = 배포 순환의 한 국면

gil 에는 정적인 "방(room)" 분류가 없다. 지금 상태는 **어느 체인이 열려 있나**로 표현된다. 체인들은 배포 순환을 이룬다:

```
개발 체인 (개발·실험)
   ↓ 닫힘
스테이징 체인 (필드테스트)   ← 닫힌 개발 체인 끝에서 열림
   ↓ 닫힘
배포 체인 (배포)            ← 닫힌 스테이징 체인 끝에서 열림
   ↓ 닫힘 → 다시 개발 체인    (순환)
```

각 체인은 맡는 **검증 깊이가 다르다**:

- **개발(dev) 체인의 verify = 기능 검사(smoke)만.** "이 기능이 동작하는가"까지. 전 주기가 도는지, 명령이 커밋을 새기는지 정도. 빠르게 짓고 돌린다.
- **스테이징 체인 = 기능 검사 이상의 엄밀한 테스트.** 엣지 케이스·필드테스트를 여기서. 닫힌 개발 체인 끝에서 열린다.
- **배포 체인 = 봉인·릴리스.** 닫힌 스테이징 체인 끝에서 열린다.

검증을 두 체인으로 나누면, 개발은 가볍게 전진하고 엄밀함은 스테이징이 맡는다.

## ⭐ 체인 전환 — 사이클을 늘리지 말고 체인을 바꿔라

한 국면이 완결되면 다음처럼 국면을 전환한다:

```
gil chain-close <chain>          # 그 체인의 모든 사이클이 닫힌 뒤에만 허용
gil chain <새이름> --purpose <P>  # 그 닫힌 끝에서 새 체인을 연다
```

1. `gil chain-close <chain>` — 체인을 완결로 봉인한다. **모든 사이클이 닫힌 뒤에만** 허용된다. 이것은 사이클을 닫는 `gil close` 와 다르다(그 위 국면 전체를 닫는다).
2. 그 **닫힌 끝에서** `gil chain <새이름>` 으로 새 체인을 연다.

**핵심 규율**: 한 국면이 완결됐으면 사이클만 계속 늘리지 말고 체인을 전환한다. 국면(개발→스테이징→배포)이 바뀌는 지점은 새 사이클이 아니라 새 체인으로 표현되어야 배포 계보가 정확히 남는다. `gil handoff` 가 이 전환을 안내한다.

## 닫힌 끝에서 조상을 이어받는다 (orphan 아님)

닫힌 체인 끝에서 연 새 체인은 **대문·존재·교훈을 조상으로 이어받는다.** 새 체인은 orphan 이 아니라 닫힌 부모 체인 위에 뻗으므로, 이전 국면의 코드·판정·교훈이 그대로 물려진다. 분기 지점(어느 체인에서 뻗느냐)이 곧 상속받는 코드를 정한다.

역으로, **닫힌 부모 체인 안에서 새 사이클을 여는 것은 거부**된다 — 새 자식 체인을 열어야 한다. 이렇게 gil 이 배포 계보가 꼬이지 않도록 강제한다. 이 거부 규칙의 개념적 배경은 [개념](concepts.md)을 보라.

## 옛 v2 이력을 v3로 이주 (gil migrate)

폴더·`cycle.yaml` 기반 v2 이력을 쓰던 저장소는 `gil migrate --from <v2-ref>` 로 그 이력을 v3 커밋 그래프로 옮긴다 — v2 체인·사이클·스텝이 v3 브랜치·종결 스텝으로 다시 자란다. 옛 v2는 별도 브랜치(예 `legacy`)에 보존해두고 언제든 재이주할 수 있다. 시그니처·매핑은 [명령 표면 — v2 이주](commands.md)를 보라.

## 층을 건널 때 무엇으로 확인했나 — `.gil/checks`

`gil merge --into dev` 와 `gil deploy` 는 **층을 건너는** 일이다. SPEC 7 은 그 자리에 검증을 두라고 말한다(개발은 smoke, 엄밀한 검증은 배포 앞에서). 그걸 문법으로 세운다.

저장소가 검사를 선언해 두면 gil 이 **직접 돌리고 종료코드로 판정한다**:

```
# .gil/checks  (대문 브랜치에 커밋한다)
dev:  python3 -m unittest discover -s tests -k Smoke
main: python3 -m unittest discover -s tests
```

- 통과하면 그 사실이 커밋에 남는다(`Gil-Checked: <명령>`). 안 남기면 다음 사람은 다시 확인해야 한다.
- 실패하면 건너지 못한다. 배포는 되돌리기 어려우므로 **마커도 새기지 않는다** — 확인 안 된 배포를 기록으로 남기지 않는다.
- 건너뛰려면 `--skip-check --skip-reason <왜>`. 이유는 필수고, 건너뛴 사실도 커밋에 남는다(`Gil-Check-Skipped`) — 안 적으면 그 커밋은 확인된 것과 구별되지 않는다.
- 선언이 **대문에서** 읽힌다. 작업트리에서 읽으면 merge 가 브랜치를 옮기는 순간 파일이 사라져 검사가 조용히 통과한다 — 게이트가 있는 척하면서 없는 상태가 된다. 검사는 저장소의 정책이지 가지의 사정이 아니다.
- 선언이 없는 저장소는 막지 않는다(없는 규율을 강요하면 이미 있는 나무가 얼어붙는다). 대신 건널 때마다 "이 자리에서 확인한 것이 없다"고 알린다.

**왜 `--verified "테스트 돌림"` 같은 칸이 아닌가.** 자유서술 칸은 생기면 채워지고, 채워지면 통과한다 — 그러다 얇은 값만 남는다(이슈 #76 이 관전 중인 병). 확인은 선언이 아니라 **사건**이어야 한다.
