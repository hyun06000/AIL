## 1. 3축 병렬 대조 — 카드 명세의 강도-이득 곡선

같은 문제·같은 모델·같은 프롬프트 형식에서 **카드 처방의 강도만** 바꿨다.

| 축 | 처방 | P5 | P10 | P4 | P7 | ail-check |
|---|---|---|---|---|---|---|
| **B** | 무처방 (v5) | 245 ✗ | 120 ✓ | — | — | 3/6 ✗ |
| **C** | 중립 문구 (v9C) | 132 ✓ | 123 ✓ | 383 ✗ | 117 ✗ | 6/8 ✗ |
| (v8) | 강한 문구 | 143 ✗ | 143 ✗ | 197 ✓ | 90 ✓ | 5/6 |
| **A** | 강한 문구 + **람다** (v9A) | **84** ✓ | **129** ✓ | **173** ✓ | **70** ✓ | **8/8** ✓ |
| — | JS 기준선 | 135 | 134 | 215 | 109 | — |

**곡선은 단조가 아니다.** 문구를 약하게 하면 P5·P10이 좋아지고 P4가 망가진다(C: P4 383, +78% vs JS). 강하게 하면 반대다(v8: P4 197 승, P5·P10 패). 문구 강도 축 위에는 전승 지점이 없다 — v6·v7·v8·v9C 네 번의 조정이 모두 같은 벽에 부딪혔다.

**A만 곡선 밖으로 나갔다.** 람다는 문구가 아니라 문법이다. 처방을 따르는 표기 비용이 사라지자 *같은 강한 문구*가 손해에서 이득으로 뒤집혔다(P10 143→129, P5 143→84).

## 2. 무엇이 비용이었나 — 두 세금

v8(조합자 문법 절 도입) 단계에서 격차가 P5 +48%→+6%까지 좁혀졌지만 넘지 못했다. 잔여 비용의 정체는 생성물에 그대로 보였다:

1. **이름 있는 fn 세금.** 람다가 없으니 모든 P5 표본이 `byCount`·`identity`·`notEmpty` 류 한 줄 fn을 2~3개 정의했다(표본당 15~25토큰). JS의 인라인 화살표는 공짜다.
2. **조합자 앵커링.** '조합자를 기본값으로' 문구가 단순 루프 문제(P10)에서도 3-fn 분해를 유도해 118→143 회귀.

람다 한 건이 둘을 동시에 풀었다. (2)가 풀린 이유가 중요하다 — 조합자 분해 자체가 손해였던 게 아니라 **분해에 딸려 오는 헬퍼 fn 비용**이 손해였다.

## 3. 명세 없음은 중립이 아니다

B축(무처방)의 실패 방식이 특히 교훈적이다:

- **토큰**: P5 3표본 245 (323·227·184). 분산이 폭발한다 — 명세가 없으면 모델이 매번 다른 전략(수동 top3 추적 / 버블정렬 / JS식 sort 콜백)을 고른다.
- **문법 정체성**: ail-check 3/6. 명세 공백을 Haiku가 JS로 메웠다 — `text.lower().split(" ")`, `pairs.sort(fn(a, b) {...})`, `word in counts`, `pairs.push(...)`.

**명세는 토큰 절감 장치이기 이전에 문법 정체성 유지 장치다.** 명세하지 않은 영역에서 언어는 JS로 되돌아간다.

C축도 다른 방식으로 같은 것을 보였다. `a plain each loop is equally valid`라는 중립 문구가 판단을 모델에 떠넘기자, P4에서 조합자와 each를 어정쩡하게 섞은 O(n²) 스캔(`each item, idx in left { if idx == leftIdx {...} }`)이 나왔다. **지침의 공백은 무작위가 아니라 모델의 기본 편향으로 채워진다.**

## 4. 조합자 이름 실측 (`experiments/tokenizer/combinator_scan.py`)

최신 4계열(o200k·qwen2.5·deepseek·phi3)에서 bare·공백 뒤 1토큰, 호출형 2토큰 기준:

- **통과**: map · filter · sort · order · rank · group · count · reduce · sum · take · slice · top · head · first · unique · reverse · find · index · any · all · none · every
- **탈락(전부)**: sortBy · groupBy · orderBy · countBy · topK · sortedBy — **파생 합성어는 예외 없이 다토큰**

→ 채택 원칙: **단일 실단어 이름 하나 + fn 인자**. `sortBy`가 아니라 `sort(xs, keyFn)`. 원칙 1·2(온전한 실단어·1토큰 실측 채택)의 표준 라이브러리 판이다.

## 5. 최종 원리

> **카드 문구 튜닝은 국소 최적의 함정이다. 명세가 비싸면 문구를 고치지 말고, 그 비용을 없애는 문법을 설계하라.**

어휘 명세 3법칙(①저수준 명세=분산 붕괴 이득 ②누락=우회 비용 ③고수준 조합 작업은 명세가 앵커라 손해)의 종결형이다. 세 법칙 모두 '명세를 따르는 표기 비용'의 함수였고, 그 비용을 낮추는 문법이 오면 법칙 ③은 소멸한다.
